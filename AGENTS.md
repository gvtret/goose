# AGENTS.md

## Build and run

```bash
cmake -B build -DCMAKE_BUILD_TYPE=Release -DGOOSE_BUILTIN_LIBS=all
cmake --build build --config Release
```

Компилятор — `build/goose` (или `build/Release/goose.exe` в Visual Studio). Он ищет стандартную библиотеку в дереве исходников, из которого был собран. Запуск программы in-process без C-компилятора: `build/goose samples/01_tour.goose`. Сборка нативного исполняемого файла: `build/goose build samples/01_tour.goose && samples/01_tour`. Программы с потоками нужно собирать именно так: TinyCC не может разместить thread-local storage.

`-DGOOSE_BUILTIN_LIBS=all` загружает и компилирует gfx, audio, ui и physics в компилятор при конфигурации. Без этого флага пакеты загружаются при первом импорте в `~/.goose`. На Linux SDL требует пакеты X11 или Wayland dev; иначе сборка пропускает gfx.

## Testing

```bash
python test/run_tests.py                          # полный набор, baseline
python test/run_tests.py --profile sanitize --cc clang  # только Linux: ASan/UBSan
python samples/run_samples.py                     # только образцы
python scripts/check_doc_examples.py docs/reference.md --run  # код из документов
```

Запускатели выбирают исполняемый файл в порядке приоритета: `build/Release`, затем `RelWithDebInfo`, затем `build`, затем `Debug`. Параметр `--exe path/to/goose` выбирает конкретный компилятор; для проверки компиляторных assert-ов используйте явно Debug-исполняемый файл. `-j N` задаёт параллелизм (по умолчанию количество CPU, максимум 32). `--batch N` задаёт число фикстур на один процесс компилятора (по умолчанию зависит от параллелизма); `--batch 1` изолирует каждую фикстуру.

Запуск отдельной фикстуры: `python test/run_tests.py --exe build/goose test/typing/generics.goose` не поддерживается напрямую; используйте фильтр по категории или `--goose-in-goose-only` для bootstrap. Запускатель находит фикстуры в `test/` по каталогу категории; имена фикстур должны быть уникальными во всех категориях.

### Что проверяет набор

Каждая фикстура: parse, dump roundtrip, typecheck. Положительные фикстуры дополнительно: генерация C, компиляция при -O0 и -O2, запуск через нативный C и TinyCC JIT, сравнение вывода с `expected/<name>.out`. Ошибочные фикстуры (`errors/`, `errors_tc/`) требуют маркеры `// error:`, совпадающие с диагностикой компилятора. Первая строка-маркер `runtime-debug` добавляет запуск с `GS_DEBUG=1`. `no-jit` пропускает TinyCC. `parse-only` пропускает typecheck.

Образцы всегда запускаются нативно и в JIT. Образец, импортирующий gfx/audio/physics/ui, пропускается, если в компиляторе нет соответствующего пакета или на машине нет GPU (`GOOSE_GFX_HEADLESS=1` выставляется автоматически).

### Обновление ожидаемого вывода

`samples/run_samples.py --bless` перезаписывает `samples/expected/*.out` по текущему запуску. Не обновляйте после изменения JIT, пока нативные прогоны не обновлены; JIT сравнивается с теми же файлами.

## Project layout

| Каталог | Назначение |
|---|---|
| `src/` | C++ исходники компилятора (~30k LOC, один translation unit из header-inline функций) |
| `stdlib/` | Модули стандартной библиотеки на Goose |
| `test/` | Фикстуры по категориям: `syntax/`, `typing/`, `lifetimes/`, `codegen/`, `optimizer/`, `runtime/`, `storage/`, `threads/`, `stdlib/`, `audio/`, `gfx/`, `physics/`, `ui/`, `packages/`, `errors/`, `errors_tc/`, `lsp/`, `goose_in_goose/` |
| `samples/` | 31 программа в порядке чтения; `data/` содержит stdin/args, `expected/` — вывод |
| `docs/` | Tutorial, справочник, спецификация, документация stdlib, implementation notes |
| `bench/` | Бенчмарки и результаты |
| `scripts/` | `toolchain.py` (общие утилиты запускателей), `check_doc_examples.py`, `package_release.py` |

| `vscode/` | Расширение VS Code (подсветка синтаксиса, LSP-клиент) |

Внешние пакеты находятся в отдельных репозиториях: [goose_gfx](https://github.com/aardappel/goose_gfx) (gfx, audio, ui) и [goose_physics](https://github.com/aardappel/goose_physics). Их `test/api_check.py` проверяет паритет модуля и C-заголовка.

## Key conventions

- **Нет кучи.** Все динамические значения живут в управляемых компилятором data stack'ах. Рост — перемещение указателя; память освобождается при выходе из области видимости. Нет аллокатора, GC или деструкторов.
- **Ссылки переживают рост.** Ссылка в растущий массив (`T[>..]`) остаётся валидной. `push` возвращает ссылку на новый элемент.
- **In-place построение.** Значения создаются в конечном месте назначения на любой глубине вызовов. Возврат растущего массива по значению не копирует его.
- **Ошибки возвращаются через вызовы.** `return E from f` возвращает из ближайшего активного вызова `f`; проверка статическая. Нет типа `Result`, нет unwinder'а.
- **Потоки не имеют общей памяти.** `thread_fn` компилируется как отдельная программа. Значения передаются через типизированные очереди через `memcpy`; гонки данных в языке отсутствуют.
- **Дженерики мономорфизируются.** Не типизированные параметры — дженерики. Функции являются сущностями времени компиляции; higher-order функции компилируются в явные циклы.
- **C interop.** `extern fn` связывает подпись Goose с C-символом. Между языками могут пересекаться только типы с поддерживаемым C-представлением. Компилятор выпускает один C-файл на программу. Заголовки пакетов (`c_headers` в `.build` файлах) могут определять inline-адаптеры с использованием сгенерированных Goose-типов (например, `mylib_Pair_g5`).
- **Заголовки пакетов.** Пакеты могут включать C-заголовки в сгенерированный C через `c_headers` в стороне `.build`. Заголовки видят сгенерированные типы и предшествуют extern-прототипам, что позволяет делать адаптеры нулевой сложности без отдельной компиляции. Пути относительные от корня пакета.
- **Маркеры фикстур.** Первая строка тестового файла: `parse-only`, `runtime-debug`, `dump-runtime`, `no-jit`, `runtime-define <name>=<value>`. Ошибочные фикстуры используют подстроки `// error:` и `// warning:`.
- **Форматер.** `goose format` перезаписывает файлы на месте; `goose format --check` завершается кодом 1, если что-то не отформатировано. `format_sweep` в запускателе тестов проверяет, что все `.goose` файлы форматируются чисто.
- **LSP.** `goose lsp` предоставляет diagnostics, hover, completion, go-to-definition, rename, symbols, semantic tokens, inlay hints и code lenses. Протоколом управляется `test/lsp_protocol.py`.

## Commit messages

Одна строка темы (до 72 символов, только что изменено), пустая строка, затем тело — не более двух предложений. Списков и повтора диффа нет. Ссылка на WI/issue — коротко, в теме или в теле.

## Agent rules

- Общение с пользователем — на русском языке; документация проекта — на русском, если не оговорено иное.
- Нетривиальную независимо выполняемую работу поручай субагенту: `explorer` (поиск/чтение), `reviewer` (ревю), `debugger` (отладка), `runner` (рутина), `tester` (тесты), `profiler` (профилирование). Inline — только тривиальные шаги и финальная сборка ответа.
- При вызове субагентов не передавай `model`, кроме явной просьбы пользователя или фоллбэка при недоступности закреплённой модели. Фоллбэк: перезапусти того же субагента с моделью текущей сессии и сообщи об этом.
- Самодисциплина: не зацикливайся. При нескольких повторяющихся попытках без прогресса остановись, переосмысли или сообщи о проблеме.
- Доказательство важнее утверждения: перед словом «готово» выполни команду и приведи её вывод.
- В текстовых файлах — только ASCII и кириллица; без спецсимволов, эмодзи и скрытых символов.
